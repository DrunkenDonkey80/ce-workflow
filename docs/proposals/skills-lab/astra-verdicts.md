## Ranked A/B shortlist

Use `openai-codex/gpt-6.1-sol` for both arms, identical disposable starting trees, effort, tools, project rules and `ultrafull` compaction. Run three paired repeats, force-load the skill in B, and add the already-decided unforced invocation check; supply referenced dependencies and document Pi invocation adaptations without silently changing the method.

1. **engineering/diagnosing-bugs — stale-answer race repair.** Seed a fixture where a question changes while its answer popup remains open. Look for an executed symptom-specific failing replay before the fix, a correct stale-answer rejection, preservation of legitimate answers and cleanup of instrumentation.
2. **engineering/tdd — requirements scheduler implementation.** Implement a fixture scheduler handling enabled/disabled requirements, independent runnable steps and human-only steps through a pre-agreed public interface. Inspect the red→green sequence, run held-out cases, then make a behavior-preserving internal refactor to test whether the added tests are implementation-coupled.
3. **engineering/code-review — review and repair a seeded change.** Supply the same fixed diff, originating request and standards to both arms; include independently scored omissions, convention violations and harmless unusual code. Compare finding precision/recall and the final repaired patch, counting both review axes’ full cost.
4. **productivity/writing-for-agents — prompt refactor followed by coding replay.** Refactor the planning instructions without altering approved decisions or runtime commands, then replay the same small feature and multi-step change through completion. Reject an apparent token saving that loses constraints, causes more questions or increases downstream work.
5. **engineering/prototype — ambiguous state-policy design and implementation.** Use a fixed script of human answers for a requirement-toggle/pause/resume scenario, then implement the selected policy. Count design contradictions exposed before implementation, acceptance failures afterward and discarded production work; do not grade the demo’s appearance as correctness.

For every comparison, report outcome quality, check results, elapsed time, **all continuation sessions’** provider tokens, cost, turns and tool calls. Separate human waiting from agent runtime, retain failed runs, and use blind outcome judging; fewer turns or a smaller prompt alone is not a win. Prototype safety checks and repository branch rules remain binding in both arms.

## Top 3 ideas to adopt regardless of skill testing

1. **Evidence-linked environment corrections — from `engineering/retro`.** When a session demonstrates a mechanical mistake, first inspect the existing check and its wiring; propose the smallest deterministic correction. Use Plan3 logs/stats as evidence and ordinary approval for changes—not automatic retros after every task.
2. **Verifiable slices with a wide-refactor exception — from `engineering/to-tickets`.** Plan coherent, testable vertical steps; when a shared-symbol migration cannot land that way, explicitly expand, migrate and contract. Fold this into the existing planner alongside the already-decided fit check, without another work store.
3. **Evidence plus reversibility — from `engineering/pr`.** For substantial changes and cutovers, show the recorded before/after result, affected consumers and whether rollback also needs state restoration. Reuse Plan3 checks and human-step questions; no compulsory PR, screenshot or new reporting subsystem.

These are bounded integration recommendations, not measured optimization claims; any changed execution or planning prompts still require the project’s end-to-end regression comparison.
