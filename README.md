# pi-work-orchestrator

Pi package for Plan3 planning and execution, research mode, context compaction and utility tools (camera, screen and image tools, Jev). Subscription usage lives in pi-control-hub (`hub/`).

Plan3 keeps durable work state in Markdown plans under `docs/plans/`. Git is the only code state. Runtime logs, telemetry, locks, exports and backups stay ignored.

## Install

```bash
pi install /absolute/path/to/pi-work-orchestrator
pi install npm:pi-subagents
# Optional: pi install npm:pi-intercom
```

`ask_user` is included (vendored pi-ask-user 0.16.0 with a pi-control-hub and intercom answer channel). If a separate pi-ask-user is loaded, ce-workflow leaves that tool in control and warns once: uninstall it to enable hub answers. Terminal questions still work with the supported 0.16.x external copy.

Run **`/wo`** for the utilities menu (Settings, compaction, Plan3 shortcuts, durable facts). Choose **Compact: Ultracompact / Ultrafull compact / Native / Native 200k** in Settings; **F8** or `/wo compact` forces manual compaction in every mode.

The **`/wo` menu title** shows `ce-workflow v<package version> · build <source fingerprint>`, captured when the extension loads; its subtitle shows the loaded package path. The fingerprint covers the manifest and extension `.ts` files, including Plan3. Changing files on disk does not change the displayed stamp until `/reload`, so an old loaded runtime cannot masquerade as the newly edited build. No Git checkout is required.

**Research mode:** Press **Alt+R** or run `/research` to toggle persistent exploration mode (`/research on|off` sets it explicitly). Research you turn on stays until you turn it off; research Plan3 turned on for planning can be left by the agent (`research_exit`) when you ask for ordinary work. `/research <question>` turns it on and offers **None** (inline agent only), **Narrow** (first other available advisor in configured list order), or **Wide** (all other available advisors). Prefix the question with `none`, `narrow`, or `wide` to select without asking. The inline model, disabled advisors, and unavailable models are excluded before selection; inherited model settings resolve to the inline model and are excluded too. With Astra/Opus/GLM configured, Wide on GLM uses Astra and Opus; Wide on another model uses all three. Exploratory ideas stay in system temp. A banner above the editor shows when it is active. The mode supplies temporary instructions for research, ideas, and plans without product implementation. Shell exploration, isolated dependency installs, archive extraction, and scratch scripts are allowed; keep their files in the system-temp research directory rather than the repository. Research is a plain on/off flag: all tools and writes stay available (the mode instructions say not to implement); only Git commit/push commands are blocked. This command guard is not a sandbox: opaque scripts and Git aliases must also obey the no-commit/no-push instructions. Early microcompaction and evidence stripping are bypassed; automatic compaction still runs once context reaches 90% of the model's window. The agent can save important findings with `research_note` into a session-specific system-temp notebook; `/research notes` shows its path, and `/research save <path>` copies it only when explicitly requested (never overwrites an existing file). Writing or updating a project plan is allowed without leaving research or asking separately. Mode state follows the session branch and stays active until you turn it off. If work is running or queued, Ctrl+R or `/research off` shows **RESEARCH STOPPING…** and keeps protection active until the agent settles; Ctrl+R again cancels the pending exit. Manual toggles never force compaction. After exit, subsequent work follows the selected normal compaction policy: Ultracompact defaults to 150k, Ultrafull compact defaults to 150k (both respect an explicitly configured threshold and smaller-model safety limits), Native 200k uses up to 200k with earlier triggering for proxy/output headroom, and Native leaves triggering to Pi. A context already above that threshold may compact on subsequent work. F8 remains available during research. Temp files can be cleared by the OS. Ctrl+R toggles research in the main editor; Pi's session-picker rename shortcut remains available inside the picker. Child sessions do not inherit research mode automatically.

**Manual-only research:** Ordinary file reads, debugging, and planning never require a research-mode transition. Only explicit user actions (`/research` or Alt+R) start research; the agent can record notes but cannot enter or leave the mode. Agent control and its tool have been removed; old `/research auto`, `/research auto on`, and `/research auto off` commands only report that removal. Research-only requests still end with an answer (and a project plan when useful), not implementation. If research is active when you want implementation, turn it off yourself. Saved research mode and notebooks still follow the session branch; legacy auto-permission flags are ignored.

**Image bridge:** Under `/wo → Settings`, choose a **Vision model**. Every main-session model, including the vision model itself, receives `img-…` references instead of image pixels from any source (reads, `screen_read`, camera, codemode `image()`): pixels replayed on every turn cost more than an occasional `process_image(image, question)` call, which asks the vision model a specific question (or, with no vision model set, the current image-capable model in a one-shot call). The original image remains in the session; the description is labelled as another model's interpretation. Images leave your machine for the selected provider only when the tool is called. The bridge applies to the main session only; subagents keep Pi's normal image handling. Reattach or reread an expired image reference; the bridge retains up to 32 recent images per session.

## Test sensitivity (every project)

Every ce-workflow session, with or without Plan3, asks for evidence that a focused regression test detects the bug—not just a green test run. A genuine failing-before-fix/passing-after-fix pair counts. Otherwise the agent selects one plausible production-code mutation for each nontrivial behavior change and uses `test_sensitivity` with the project's existing test executable and arguments. Documentation-only work needs none; explicit no-tests requests and missing safe prerequisites remain disclosed gaps. This is always-on guidance plus an execution helper, **not a hard completion gate**.

The helper copies current Git tracked and nonignored untracked files, including uncommitted edits, into system temp; applies one unique exact replacement there; and runs baseline → mutant → restored. `caught` requires a green baseline, exit 1 with the declared assertion text absent from passing output, and a green restored run. Green mutants survive. Killed/truncated runs, recognized syntax/import errors and unmatched failures are inconclusive. The agent must still inspect the assertion and judge whether the mutant represents a real bug: output matching is not a universal test-result parser. A survivor calls for a stronger test or a justified equivalent-mutant explanation, not a claimed pass.

Only the temporary copy is patched. No checkout, stash, branch, commit or dependency install occurs. Git metadata, ignored fixtures and symlinked source are not copied; unsupported layouts need the project's own safe isolated red/green check. Optional `dependencyDirs` (relative to Git root, such as `node_modules`) are linked and cannot contain tracked source or the mutation target. **This is not an OS sandbox:** test commands retain normal machine permissions, and linked dependencies are shared. Use only trusted local commands with disposable fixtures, never live services. Each run has a maximum 120-second timeout and 1 MiB output cap; snapshots are limited to 20,000 files and 512 MiB. Source copies are cleaned up; bounded logs, source/snapshot hashes and `result.json` remain under the returned system-temp `evidenceDir`. Evidence identifies that snapshot, not future edits or protection against every bug.

Focused self-check: `node "scripts/test-work-test-sensitivity.mjs"`. Reload Pi to load newly installed or edited extension code. No runtime, token or cost improvement is claimed.

## Project camera (provisional)

Under **`/wo → Settings`**, open **Camera (project only)**, select the exact camera and explicitly enable it (default OFF). On Windows that is a webcam through an existing FFmpeg installation with DirectShow. On a Mac it is an iPhone or iPad on a stand (USB or Wi-Fi): its Camera app is opened, left open, and its viewfinder read as screenshots through mobile_act's helper. Never downloads a backend or falls back to another camera. Selection is not permission: each bounded request needs native local consent, or an unexpired previously approved time grant. Permission choices are one shot/burst/watch, one hour, current local day or 48 hours. RPC, print and headless sessions cannot acquire, including with saved grants.

- **`camera_capture`** returns a still or up to eight spaced stills. Default full field of view has a 1024-pixel maximum edge; `fullSize: true` requests native detail without silent downgrade. Crop coordinates are native source pixels; explicit output sizes cannot upscale. Hardware closes between burst shots, so reopening/warm-up adds latency beyond `intervalMs`. With a phone, `lockAt {x, y}` (source pixels) long-presses the viewfinder first to lock focus and exposure there (AE/AF LOCK), for a dim display or a dark room.
- **`camera_watch`** requires an explicit `deadlineMs` (maximum 48 hours, capped by consent expiry). It returns only after warm-up and baseline readiness: operate the device **after** that response, then let the model idle—no polling. Adaptive mode emits at most an initial batch plus final delivery, coalescing them when busy. `mode: "settled"` emits only one fresh final image after observed activity and `quietMs` of visual quiet (default five seconds). Initial idle, stalls, disconnects and expiry never mean successful completion. Quiet can also mean a paused/jammed printer; confirm job status using existing caller authority.
- **`camera_stop`** stops the watch and discards pending wakes without revoking a time grant. Settings **Revoke camera permission / stop** also revokes permission. Escape, session/branch changes and reload cancel owned acquisition; failed release stays visible and retryable.
- **`camera_recover`** reattaches an existing unexpired frame UUID in the same project, never silently recaptures missing history. Manifests survive image stripping; frames reach the model through the image bridge, whose answers are interpretations rather than direct verification.

The active camera warning distinguishes ARMED from red CAPTURING/WATCHING and remains through confirmed release. Watches sample locally but never record a video/audio file. Crop limits shared pixels, not the sensor field of view. Dedicated temporary images expire after approximately 24 hours; old tail images are immediately deleted. Cleanup cannot erase provider copies or Pi session history.

**Not hardware-qualified yet:** sampling defaults (320x180 at 10/s), warm-up, noise thresholds, brief-state observability and sustained load are provisional. Use crop/tile settings for small LEDs; not every brief state is observable. Retention protects up to 20 initial images, eight rolling-tail images and one final image, with 256 lifetime saves and finite byte limits; exhaustion thins evidence, not detection. No live camera, printer or red-warning qualification is claimed.

## Optional Jev tools (experimental)

Under **`/wo → Settings → Optional Jev tools`**, explicitly enable uploads globally (every project without its own setting) or in project scope for one project. A project value overrides the global one in both directions, so a project can opt out of a global On. Default Off. Use native **`/login → OpenRouter`** for credentials—never put a key in settings. The panel shows configuration status, not a paid connectivity test. Default classifier: `openrouter/typesafe/jev-1.13`; no silent provider/model fallback. Requires Pi's native classifier/hidden-tool APIs, Node's `path.matchesGlob`, and `rg` for evidence search.

These are ordinary optional tools, available in direct sessions and Plan3, including codemode. No automatic calls, read replacement, work items, or per-turn prompts. Off hides both wrappers and guards execution; it does **not** disable Pi's separate native `models.classify()` API. Settings changes abort outstanding wrapper requests. `/reload` loads updated code.

- **`jev_triage`** accepts up to 32 independent `jobs`, each with `id`, `questions`, optional JSON `state`, and optional `sources: [{path, startLine?, endLine?}]`. Several sources in one job form an explicit cross-file bundle. Up to 32 questions share that single provider invocation.
- **`jev_evidence`** accepts explicit relative `scopes` (files/directories/globs), `unit: "file" | "window"`, optional `pattern` (literal by default, `regex: true` opt-in), and optional `questions`. It honors rg ignore rules, captures exact evidence locally, and returns bounded ranked excerpts. `rankQuestion` selects the ranking question; choice ranking also needs `rankChoice`. Without questions it does lexical retrieval only, without classifier calls.

Question example: `{"relevant":{"type":"bool","instructions":"Does this supplied source expose battery temperature?","criteria":{"true":"Exposes temperature","false":"Does not expose temperature in the supplied scope"}}}`. Native `choice` uses a label-to-description map; `score` uses ordered descriptions. Answers classify supplied evidence—they cannot extract arbitrary quotes, prove repository-wide absence, certify tests, or authorize actions. Bool 0.2/0.8 bands are uncalibrated. Read the cited source normally before editing or quoting; hidden classifier reads do not satisfy read-before-edit.

Sources leave the machine for OpenRouter/TypeSafe. Canonical containment, secret-path/content filters, binary rejection, and bounded reads reduce risk but do not certify arbitrary files as secret-free. No custom raw exchange logs; inline JSON still exists in the normal tool-call transcript. Source captures are capped at 256 KiB; invocation state **plus questions/envelope** at `min(24,000, floor(contextWindow × 0.75))` UTF-8 bytes. Narrow ranges/windows rather than treating a clipped prefix as complete. Evidence inventories are bounded (128 files, 32 classified candidates, 10 returned excerpts, 24,000 output bytes); incomplete scans, omissions and provider failures are explicit. Whole-file anchors do not invent matched line numbers. Hashes/excerpts refer to captured bytes, not a guarantee the file remains unchanged.

Concurrency is 4, with 30-second request and 120-second tool deadlines; no wrapper retries. Native usage is carried once at the enclosing tool-result level; missing usage is unknown, and reported cost is a catalog estimate, not billing. Exact search, LSP and compilers remain authoritative for their respective checks. **No performance improvement is claimed yet**: the paid, agent-choice AI-Wedge-derived comparison remains approval-gated.

Offline self-check: `node "scripts/test-jev-tools.mjs"`.

## Screen read tool

`screen_read` returns a small PNG for visual testing: an app window (Windows and macOS; also minimized or in the background, without focusing or showing it; on macOS through a small Pi Screen Helper app that asks for Screen Recording permission once, so the grant survives Node upgrades and covers only screenshots), the current headless agent-browser page or element, an Android screen, or any iOS Simulator, iPhone or Android device through mobilecli (`target: "device"`). `maxEdge` (default 1024) downscales and `region` crops in source pixels. With no window selector it lists windows. `/resume3` tells agents to launch test apps minimized or headless.

`video_digest` (a YouTube coding video as transcript plus rebuilt on-screen code and diagrams) now lives in the separate yt-ingest Pi package. Where that package is installed, `tools_enable` turns it on like the tools above.

`mobile_act` drives an iOS Simulator, a real iPhone or an Android emulator/phone through [mobilecli](https://github.com/mobile-next/mobilecli): list and boot devices, launch an app, read the screen as a list of labelled elements with accessibility ids and positions, tap, long press, type, swipe and press hardware buttons. Each action returns what changed on screen (`settleMs`, default 500; 0 skips it), and refs stay the same while an element stays on screen. Actions also take a `query` (`#id` or label text) to find and act in one call, `wait` waits for text to appear or disappear, `ocr` reads on-screen text with Apple Vision for controls the accessibility tree misses (macOS; a `query` falls back to it), `launch` and `relaunch` check that the app really closed and came to the front (an error otherwise) and return its first screen, every result names the app in front, an `APP CHANGED` line heads it when another app took over (yours closed or crashed) and an `ALERT` line when an alert is open, and taps on overlapped elements such as a fanned card hand land on their visible part. For test loops that must stop on the first thing that goes wrong, `checkpoint {name}` saves the current screen as the good state on first use (element types, labels and ids plus the app in front; `visual: true` adds a 16x16 color grid without the status bar, for drawn screens without accessibility labels) and compares later calls against it, while also watching the app's crash reports (iOS simulator and iPhone, Android crash log). `wait` takes `failOn` texts, `failOnAlert`, `expectApp` and `stableMs`. A checkpoint difference, a new crash report or a failed guarded wait stops the run: the screen and any new crash report are saved under `~/.cache/ce-workflow/mobile-act/failures/`, and that device's breaker refuses launches and input until `resume`, so a script cannot keep looping past an error. For long repetitive flows, such as playing a game, the agent writes the loop once in codemode with `tools.mobile_act` calls instead of spending a model turn per step. mobilecli ships with ce-workflow as an npm dependency (macOS, Linux and Windows, x64 and arm64), so nothing to install; its helper agent installs by itself on simulators and only after a Yes on a real iPhone, which needs a development provisioning profile with a wildcard App ID that includes the phone. Without that profile, or when mobilecli's agent will not start, a real iPhone or iPad on a Mac uses ce-workflow's own helper over its CoreDevice tunnel, USB or Wi-Fi alike (built once per device with the profile Xcode made for it, after a Yes), and keeps that route in later sessions; `list` marks it `USB helper`. A Wi-Fi helper that stops answering is started again once. `list` also warns when another mobilecli on PATH has a different version, since both share one daemon and each restarts it for the other. When the helper will not start on a real iPhone, mobile_act says so at once instead of retrying for minutes: it names iOS's "Enable UI Automation" passcode prompt (shown once after each restart) when it is on screen, restarts a mobilecli daemon whose link to the helper went stale and retries once, and otherwise tells whether the phone is locked or the helper crashes as it starts.

`app_act` does the same for apps on a Mac, through Accessibility: `menus` lists every menu item with its path, hotkey, check mark and whether it is available right now, and `menu` runs one by path (`Product > Archive`). `snapshot` reads a window as labelled elements with refs, and `press`, `type` and `key` act on them; each action returns what changed. It works with the app in the background and never moves the mouse. A small signed helper, Pi App Helper, makes the Accessibility calls, so macOS asks for that permission once, for the helper rather than for node. You allow each app once per session, and buttons such as Upload, Distribute, Submit or Delete ask first; you can allow them for that app for the rest of the session. Password fields are refused. With the screen locked it refuses and asks for an unlock, since apps then show no real windows. A button that lists the press action but refuses it is clicked in its middle instead, posted to the app so the pointer stays put. On Windows it uses UI Automation instead (no helper to install): `menus` lists classic menu bars only, `key` brings the window to the front for a moment and asks you each time, and slow-to-describe apps such as OneCommander read in about two seconds. A classic Windows button that offers no UI Automation action (a launcher's error box) is clicked through a window message, still without moving the mouse. `wait {query, gone?, failOn?}` reads the window until the text shows or goes, and fails on a `failOn` text or the timeout.

## Browser fetch

`browser_fetch {url, images?}` loads a page in **your own browser** (Helium, Chrome, Edge or Chromium, your everyday profile and cookies) through the Pi browser fetch extension, so Cloudflare and similar bot checks see a real browser. It returns the page's text (up to 100 KB), links and image URLs, marked as untrusted data. With `images: true` it downloads up to 30 images (8 MB each, 60 MB total) to `%TEMP%/pi-browser-fetch/<request>/` and returns their paths. Read-only: no clicking or typing.

- **Set up:** `/wo → Settings → Browser access → Install or update the browser extension` registers the native host for each browser (Windows; its launcher goes to `~/.pi/agent/browser-fetch/host/` and runs this package's `browser-fetch/host.mjs`). Then open `chrome://extensions`, turn on Developer mode and **Load unpacked** this package's `browser-fetch/extension` folder; after a package update, reload it there. **Open the extension folder** in that menu shows it in Explorer (Finder, or your file manager). The tool appears only after Install (`/reload` once); until then the menu says the extension is not registered (ID `dmbpeaidhpenhihgngkgekaieninaapk`). Node must be installed. The agent opens an inactive, muted tab per request and closes it after reading.
- **Approval:** each new site asks through `ask_user` (terminal, hub and phone) with the full URL: allow this request once, allow the site for 1, 2 or 4 hours, always allow it, deny, or block it. No answer in 5 minutes is a deny. Parallel requests to one site share one question; "once" covers only its own request. Subagents and other sessions without a UI only get sites already allowed.
- **Never opened:** a built-in block list of mail, sign-in, password-manager, bank and payment sites (with subdomains), plus sites you add; local names, private, loopback and link-local addresses (also through DNS, best effort: DNS rebinding after the check stays possible). A redirect or script navigation to another site is stopped in the browser before any request reaches it and approved separately (at most 5 per request); the page that comes back must be on an approved site. Images on other hosts are covered by the page approval but sent without your cookies; image redirects are not followed.
- **Pause:** the extension's toolbar button pauses all agent browsing (badge `II`); running requests stop and new ones fail with "paused by the user".
- **Policy and log:** grants and your block list live in `~/.pi/agent/browser-fetch/policy.json`, shared by all sessions (Browser access revokes grants and edits the block list). Every request is logged to `log.jsonl` there with time, project, URL, final URL and what allowed or refused it.

### Browser act

`browser_act` lets the agent operate one site in your own browser, logged in as you, after you grant that site for 10, 20 or 30 minutes (never "always"; a control grant is separate from a read grant). It works in its own background tab, so it never takes over your screen, in a blue "Pi" tab group (click it to watch), through the browser's debugger, so the browser shows its "is debugging this browser" bar while the agent drives. Your other tabs are never touched. After a package update, reload the extension in `chrome://extensions` to give it the `debugger` and `tabGroups` permissions. It can upload files too, and you confirm every upload after seeing each file and where it goes: PNG, JPEG, GIF or WebP images inside the project folder can be allowed for that folder for a while, any other file (a build, a document, anything outside the project) is asked every time. If the browser refuses the files, turn on "Allow access to file URLs" for the add-on in `chrome://extensions`. Sending, deleting, publishing and similar clicks ask first; you can allow them on that site until its control grant ends (payment fields still ask every time). `snapshot` waits for the page to stop loading data, and `wait` waits for given text to appear or disappear, which single-page sites such as App Store Connect need; a `wait` whose text never shows, or with a `failOn` text on the page, fails so a script stops there. `click`, `type`, `select` and `upload` take a `query` (plus `role`) instead of a ref: it must name exactly one element on the page now. Each action returns what changed on the page (or the new page), so no extra snapshot is needed.

`browser_search {query}` searches Google in your own browser (a hidden background tab that closes afterwards) and returns the first results page as a numbered list: title, real URL, site, date and snippet. `image_search {query}` returns one contact-sheet image of up to 30 numbered thumbnails, a numbered list (title, site, size, original URL) and a result-set id; `image_search {set, save: [numbers]}` then downloads those full-size originals from that exact set, without searching again, to temp files (no cookies; blocked and local addresses refused; 8 MB each). You allow google.com once (it can be "always"). Searches run one at a time per browser, 2 s apart; after a Google CAPTCHA they pause for 5 minutes (doubling up to an hour), and every failure tells the agent to use `web_search` instead. pi-web-access stays installed as that fallback and for `fetch_content`. The toolbar pause button stops searches too, and each one is logged.

- **Actions:** `open {url}`, `snapshot` (the page's buttons, links, fields and headings as `[e12] button "Save" @(x,y wxh)`), `find {query, role?}` (searches the last snapshot), `click {ref}` or `{x, y}`, `type {ref, text, submit?}`, `select {ref, value}`, `scroll {direction}` or `{ref}`, `screenshot` (a PNG path under `%TEMP%/pi-browser-fetch/`), `back`. Refs stay valid until the page address changes.
- **Safety:** typing into password and one-time-code fields is refused. Clicks and submits that buy, pay, order, send, delete, remove, publish, post, transfer, confirm or subscribe (English and Bulgarian), or touch a card-number form, ask you first; a mislabelled button can slip past this word check. Each acting step is checked, then executed only if the element did not change. A link or redirect to another site is stopped before it loads and needs its own grant (then the agent repeats the action); new tabs the page opens are closed. Leave-page warnings are accepted; other page dialogs are cancelled and reported. Elements inside iframes are listed but cannot be used.
- **Ending control:** the grant running out, the toolbar pause button, cancelling the debugging bar, closing the tab or ending the Pi session closes the tab. `/wo → Settings → Browser access → Controlled sites` revokes a grant; the next action stops. Every action is logged to `log.jsonl` with the site, element name and decision, never the typed text.

Self-check: `node scripts/test-work-browser-fetch.mjs`.

## Plan3

Plan3 is the primary planning/execution flow: one living Markdown plan per task in `docs/plans/` (`plan3: true` frontmatter), worked by the current agent and model. No work items or gates; statuses and checks are agent-reported. Execution commits locally (never pushes) the files it changed after each verified step and checkpoint, picks a recorded `assumed` default for reversible choices instead of asking, and implements each step only to its acceptance (extra hardening goes to Backlog).

- `/plan3 <request>` creates a draft, turns research mode on and plans (no product code). If an open plan looks like the same request (word overlap ≥ 0.5), it offers **Resume that plan**, **Merge as follow-up** (appends the request to its Amendments and plans again) or **Create new anyway**.
  - **Size first**: after a short look, the planner recommends a size and a compact **Plan size** dialog asks you to confirm or override it (night mode and headless runs take the recommendation): **Tiny** deletes the fresh draft, turns research off and makes the change at once, ending with the diff and the checks run (no commit); **Plan** plans normally; **Map** turns the draft into a multi-session decision map. The pick is recorded as a `D-size` decision. Only a fresh `/plan3 <request>` is sized; resumed, captured, converted and merged drafts are not. One change later is allowed: when grilling a normal plan turns up more fog than one planning session can hold, the planner offers to turn the draft into a map in place (Yes/No), keeping the request, decisions and answers so far (`D-map`).
  - **Map plans** (`kind: map`) chart foggy work instead of building it (work whose way is known stays a normal plan, even across several sessions): a one-line Destination, Notes every session should read, typed decision tickets (research, prototype, grill, task; prototype and grill are `[human]`) run strictly in order, Not yet specified for the fog and Out of scope. Executing a map resolves one ticket at a time and graduates the fog into new tickets; it completes only when no ticket is open and the fog is empty, ending with a Handoff list of `/plan3` requests for the normal plans the Destination needs.
  - **How planning asks and plans**: facts are the agent's job, decisions are yours. Questions come in rounds of independent decisions with context and a recommendation. A **project care** fit check per touched module weighs a prefactor against the quick patch and records the choice; steps are thin end-to-end slices that keep the tree working, with wide refactors done as expand, migrate, contract.
  - **Project language**: planning reads `GLOSSARY.md` and `docs/adr/` when present and records settled project terms and ADR candidates (decisions that are hard to reverse, surprising and a real trade-off) in the plan. `/plan3 finish` offers them in a **Project docs** checklist and writes the ticked ones only after you confirm **Plan ready**; the files are created when there is something to write, and nothing is offered twice.
- **Phase models and coding effort** (`/wo` → Settings → **Plan3 → Planning model / Coding model / Coding effort**, global or per project; project wins per setting): starting planning (`/plan3`, `/resume3` on a draft, optimize) switches to the planning model; `/resume3` execution switches to the coding model and effort. Unset ("same as session") keeps the session's own model or effort, which Plan3 remembers and returns to; a manual `/model` or effort change becomes the new session value. It switches only when a run starts, because a different model or effort level has its own prompt cache (measured on GPT-6.1 Sol; documented by Anthropic) and every switch re-reads the context uncached once. A model without configured auth is skipped with a warning.
  - **Per-plan override**: `/plan3` → pick a plan → **Models** sets them for that plan only, as `planningModel` / `codingModel` / `codingEffort` front-matter keys (plan wins over project and global). They apply whenever a run starts on that plan; switching to another plan restores that plan's settings, and code keeps the keys when the agent rewrites the plan.
  - **Phase tags**: the planner ends every `###` phase heading with `[think]` (judgment work: design decisions, metrics or experiments, running, evaluating or tuning agents, LLMs or prompts, diagnosing unclear failures; runs on the planning model at high effort) or `[code]` (runs on the coding settings). Code switches at `/resume3` and mid-run (turn end) when the current step crosses into a phase with a different tag. When any unfinished phase is untagged (older plans, phases added later), `/resume3` first runs a tagging turn: compacted first, as its own run on the planning model in research mode; when it ends, code leaves research and starts execution as a new run. `/resume3` also lists unfinished `[code]` phases whose text reads like judgment work (3+ keywords such as benchmark, agents, prompts, metric). Checked ones switch to `[think]`, and each phase is asked once (`tagsChecked` in the front matter). Edit tags by hand any time.
- **Review before work**: when Finish planning shows *Plan ready* for a plan that was never reviewed (no `reviewed:` front-matter date; `/plan3 review` writes it), the dialog offers review first (so does `/resume3` or Start work on a ready, never-reviewed plan, with *Start work without review* as the alternative): **Review first** when one other Plan model is available, or **Review with one advisor** / **Review with all N advisors** when there are several.
- **Enter runs slash-command arguments**: Pi runs a command on Enter only when you complete its name; picking an argument (`/wo sett`, `/plan3 con`, `/effort me`) just filled the line and needed a second Enter. `extensions/enter-runs.ts` stacks an autocomplete wrapper (`ctx.ui.addAutocompleteProvider`, Pi's editor is unchanged) so the first Enter fills and runs. Tab still only fills; `@file` and directory completions keep filling.
- **Stop guard** (outside night mode): in a session where `/resume3` started executing a plan, a stop after a run that changed something (plan file, HEAD or uncommitted diff) while runnable steps remain gets one continue asking for the reason; the agent either states a real reason and stops or carries on. Stops with no new work (that reply, a chat answer), Escape and errors are left alone.
- **Night mode** (**Alt+N** or `/night [on|off]`) runs the current ready/active plan unattended. It is not a sandbox: the agent keeps your files, network and credentials, and the blocked-command list is a guard, not isolation. Turning it on shows a dialog with the plan and the project rules from `.pi/night.md` (edit, use or skip them), turns research mode off and keeps Windows awake. Idle, it resumes the plan; mid-run, the agent gets the night instructions (plus project rules) as a steer and keeps going. At each final stop Pi continues it with the same message until the plan is complete, no runnable step is left, two continues change nothing (plan file, HEAD, uncommitted changes), or Escape cancels; provider errors after Pi's own retries are retried every 30 minutes. `ask_user` and reboot/shutdown/sleep commands are blocked: questions go into the plan as Deferred questions for `/plan3 resolve`. A banner above the input shows `NIGHT MODE`, `NIGHT PAUSED: <reason>` or `NIGHT COMPLETE`; Alt+N turns it off. No deadline or continuation cap.
- **`[human]` steps** need only you: your presence, a physical action, approval or authorization. Night mode treats them as blocked and pauses when nothing else is left. Outside night mode the agent asks about each one with `ask_user` instead of stopping. Turning night mode off always tells the agent you are back, even after a pause. A plan that execution left `blocked` resumes as execution, not planning. `/resume3` on a plan with open questions first offers **Answer open questions** or **Resume work**.
- **Requirements** are external things steps need that are not files: a reboot, a printer on COM23, the user seeing a printout, a VM. They are listed in the plan's `## Requirements` section. A `needs:` line under a phase heading, or a `  - needs:` sub-line on a step, says what that phase or step needs. The agent adds them with `plan3` action `requirement`. That marks the current step and asks you once whether to allow it; in night mode the answer is no without asking. Code only schedules steps whose requirements are on. **Alt+A** or `/plan3 needs` opens the checklist; changes made during a run are sent as a steer. Day and night each keep their own remembered set in `docs/plans/logs/<id>.needs.json`. Night on and night off both show that night's or day's checklist. Requirements nobody has set yet start off. This decides only what gets scheduled; it does not block any command.
- **Statistics**: while `/resume3` executes a plan, code records where the time goes in `docs/plans/logs/<planId>.stats.json` (kept with the plan when it is archived). It records model thinking (request sent → first text or tool call) and acting per model and effort, with tok/s, cache hit % and cost. It also records tools by elapsed and summed time, tests and build (classified from the command line), the slowest commands (secrets redacted, at most 200 kept), waiting for you in dialogs (separate from model time), compactions, and per step: time, replies, failed tools and models. When the same long command (2+ min) runs twice in a row with different arguments and no edits between, code sends one speed hint per command family to the agent. The hint suggests running the rest in parallel if the runs share no state, and keeping them sequential otherwise. The viewer lists the hints sent. Open it from the plan's **Statistics** item in `/plan3`; **Tab** in the plan list switches between open and finished plans. Night mode ignores stats files when it checks for progress.
- `/plan3 write [topic]` (aliases: `/plan3 planify [topic]`, `/plan3 create [topic]`) captures the discussion already in this chat into a new draft and turns research mode on, **without Plan3's pre-compaction** or the duplicate-plan resume/merge detour. The agent saves settled requirements, decisions, rejected options, examples, references and known results before investigating gaps; it does not restart research. An optional topic selects which discussion to capture. `/plan3 finish` remains the ready/compact handoff; native context-limit protection still applies.
- Agents create plans only through the `plan3` tool's `create` action, which writes the standard template with a stable id; writing a new `plan3: true` file into `docs/plans/` with the write tool is blocked.
- `/plan3 convert "C:/path/to/existing-plan.md"` imports an existing text plan (relative paths work too) into a **separate draft**, keeping the original unchanged. Passing an existing `.md` path directly, with or without quotes, does the same when its filename contains `plan` (case-insensitive); explicit subcommands still take priority. Code saves the full source snapshot to the plan's sidecar log (`docs/plans/logs/<id>.md`) before any agent turn, so the plan never carries it; no pre-compaction or duplicate-plan routing. The conversion applies the same lean-plan rules as **Optimize** (below). A dedicated conversion prompt preserves scope, settled decisions, progress and evidence, reviews against the current repo, and asks about genuine gaps rather than replanning from scratch. Imported completion claims remain source-reported, not newly verified; the copy stays draft/blocked until `/plan3 finish`. Already-Plan3 files can be re-converted the same way. Plans converted before the sidecar log may still hold an `Imported plan` section; its historical placeholders do not block finishing.
- While actively planning a draft/blocked plan, exact bare words **`finish`**, **`done`**, **`resolve`**, **`ideas`**, **`review`**, **`ideas all`** and **`review all`** run the matching `/plan3` action. They stop working as shortcuts once planning finishes. Ordinary sentences (such as “review the code”), image inputs and extension-injected messages remain normal input.
- `/plan3 ideas [all] [focus]` — read-only, fresh-context advisors propose ideas while the current agent writes its own independently. The agent collects every advisor's result, merges overlaps with source attribution, and supplies full explanations: what each idea does, benefits/examples, drawbacks/risks, implementation/files, cost, recommendation, and proposed requirements/steps. Code saves them in **Ideas**, then opens **one fully expanded, scrollable `ask_user` popup per idea**, with **Accept**, **Reject**, optional comments and custom text always available. The matching button shows **(Recommended)** when the stored recommendation explicitly begins with Accept or Reject; neutral/unclear recommendations receive no badge. The badge is advice, never an automatic decision. Idea popups use 98% width and all available height minus one-row margins, omit duplicated titles/status/context labels, and put section text directly under compact headings; the saved plan retains the full records. Plain acceptance immediately adds the requirement, steps and a Decision in code; rejection is recorded without adding work. Any custom text or selection with a comment is saved as **commented**, not silently accepted: one subsequent agent pass interprets intent, answers questions and records accepted/rejected/answered dispositions. Answered is not approval. Cancel leaves the remaining ideas pending; `/plan3 ideas select` resumes saved pending/answered ideas and reconciles comments without rerunning advisors. `/plan3 finish` refuses unsettled ideas.
- `/plan3 rework [target]` plans a test-guarded rework of one part of a grown, messy project, following the shipped [rework recipe](docs/proposals/2026-11-05-rework-recipe.md). The aim is a **deeper module**: a smaller interface, rules moved from callers into the module, and fewer files touched by the next realistic changes. The phases:
  - **Map** finds candidates with the deletion test and counts the files each likely future change touches.
  - **Characterize** records the current behavior as tests and baseline numbers.
  - **Design** compares several interfaces in parallel.
  - **Build**, **Replay**, **Switch** and **Retire** wait behind `R-design-approved`, `R-cutover-approved` and `R-retire-approved`. You turn each one on with Alt+A, so neither night mode nor `/resume3` runs them first.
  - Without a target, Map picks one.
- `/plan3 review [all]` — the advisor reviews the plan against the repository; the current agent validates each finding, applies accepted corrections and records every disposition in Amendments.
- `/plan3 resolve [id]` opens the **actual `ask_user` popup and custom-response editor directly, before any model turn**, using the vendored ask_user popup (or a supported external pi-ask-user 0.16.x copy when still loaded). Stored Open questions, context, recommendations and options are supplied without restarting research: Blocking first, then Deferred. Questions explicitly marked `  - Independent: yes` share reviewable batches of 2–4; older/unmarked questions are asked singly rather than assuming independence. Submitted answers move to Decisions in code, preserving their stored context and labeling them user-supplied, not independently verified. Cancelled batches, skipped/kept-open items and changed questions remain open. After the popups, one agent handoff reconciles submitted answers and needed plan changes; complete plans are not reopened. **Discuss with agent** leaves its question open and starts discussion after the submitted popup instead of asking the remaining questions first. Missing/incompatible packages produce a clear error, never another pre-popup thinking prompt. Open items are top-level bullets, or prose that is not None or a placeholder. The planning hint shows `/plan3 resolve <id>` and the open-question count, the `plan3` tool reports `openQuestions`, `/plans3` offers **Resolve open questions (N)**, and execution replies end with `Next: /plan3 resolve`.
- `/plan3 finish` (or `done`) checks the plan in code (original request, no placeholders, Blocking = None, at least one step), marks it **ready**, turns research off, compacts above 20k tokens and makes it the current plan. A **Plan ready** dialog offers **Start work** or **Not yet**; headless mode prints the exact `/resume3 <id>` command. No automatic execution or ready status from the agent. Planning replies get one code-owned, state-aware next action: answer questions, settle saved ideas, continue planning/design, or finish. Ideas/review are optional, not mandatory transitions; legacy trailing model command lists are removed. Planning prompts carry the lean plan shape (step lines under 200 characters, qualification as separate `[blocked]` steps, Backlog, one checkpoint under 1.5 KB), and every Plan3 prompt states that its run instructions bind only that turn and never reword a recorded decision. When a planning turn (plan, write, convert or design reconcile) leaves a draft that would pass finish, code runs the shape checks; a converted or optimized plan is also compared with its source snapshot for glued words and slash chains. The first failure gets one repair turn; a later failure only warns and never blocks finish.
- `/resume3` continues the current plan; `/resume3 <id|filename|path>` picks another. Draft/blocked plans resume planning with research on; ready/active plans execute with research off. Repo paths named in the plan that changed in Git since its last update are listed for re-checking first. Execution receives a compact **resume packet** instead of an instruction to reread the whole plan and its sources. The packet holds constraint sections in full (request, goal, decisions, open questions, validation, checks, resume context), one line per step, and the full current step. It lists omitted sections with their sizes, which the agent fetches on demand. The prompt says to continue to the next runnable step after each verified one, and to stop only for a required user decision or action, a prerequisite that blocks *all* remaining work, completion, cancellation or a hard limit. Marking a step done requires a one-line `summary`: the step shrinks to that line, and their notes and checks move to the sidecar log. The `plan3 checkpoint` action (and any section write to Resume context) replaces the single current checkpoint, and old text moves to the log. `next` closes the step actually finished: it needs `id` when several are wip, and it starts a new step only when none is wip. Steps under `## Backlog` never count. Tool results warn about open plans over 40 KB.
- `/plans3` (or `/plan3` alone) lists plans: current first, then open plans by last update, then complete ones, each with done/total, a progress bar and timing (`active 3d · touched 2h ago`). A plan offers **Resolve open questions** first when needed, otherwise **Finish planning** for drafts. Ready/active plans offer **Start work**/**Continue work**; draft **Resume** continues planning. It also opens **View** (open its Markdown file in the OS default app, including archived plans; no agent turn), **Optimize** (open plans; also `/plan3 optimize [id]`): code first appends the full plan to the sidecar log and turns research mode on (for its larger context window), then the agent rewrites it as a lean current work document. The rewrite keeps one checkpoint, one-line done steps and active decisions only, splits implementation from VM/hardware/human qualification, moves out-of-scope work to Backlog and adds a Checks section; no product code or checks run. After that agent turn, code verifies that every prior step and decision ID still appears, no open question was removed and the status is unchanged. Over-strict requirements (measure-first rules, test corpora, hardening beyond the request) are never relaxed by the agent; each becomes a Deferred question with Keep as is, Relax (a concrete default) and Move to Backlog options for `/plan3 resolve`. It also lints for glued words, slash-chained lists, duplicated prerequisites, step lines over 200 characters and a Resume context over 1.5 KB. The first failed check sends the agent one repair turn listing the exact problems, so the result does not depend on how well a given model follows the prompt. Code then reports the size before and after and restores the research mode `/resume3` would use; a failure that survives the repair points to the snapshot. The resume packet clips other steps' lines to 200 characters. Other actions: **Force finish** (when a product diagram exists, reconcile it with actual code first, then archive; unfinished steps stay listed in Amendments) or **Delete** (confirmed). When the legacy store has unfinished roadmaps/tasks, a **Convert legacy work (N)** row writes them as Plan3 plans (closed → `[x]`, in progress → `[wip]`, blocked → `[blocked]`, deferred → Deferred questions; `source: work:<id>`); the old store is never modified.

**Frontend design:** the package includes the pinned Anthropic `frontend-design` skill with its Apache-2.0 license and [provenance](skills/frontend-design/UPSTREAM.md); no separate install is needed on each computer. Pi advertises its description and loads the full guidance only when needed. Planning consults it for new or substantially redesigned web UI and records the chosen direction, reused tokens/components and skill reference—not the skill text. Execution uses it as needed without reopening settled design choices. Explicit briefs and existing design systems win; routine fixes preserve existing UI, and native/TUI work follows platform/project conventions. Capture/conversion remains preservation-first. `/skill:frontend-design` loads it explicitly.

**Review and debugging skills:** two skills adapted from [Matt Pocock's skills](https://github.com/mattpocock/skills) (MIT, provenance in each `UPSTREAM.md`) ship with the package and load only when the task matches. `two-axis-review` reviews a diff on two separate axes, Standards (the repo's documented rules plus a baseline of code smells) and Spec (missing, wrong or unasked-for behaviour against the request or Plan3 plan), and reports them side by side; it costs about three times a plain review, so ask for it when the review matters. `diagnosing-bugs` makes the agent reproduce a bug with one command before theorizing, prove the cause one change at a time and run the regression test red before the fix. Both were picked by blind A/B runs in the skills lab ([results](docs/proposals/skills-lab/results.md)).

Only the `/resume3` execution prompt includes test/build guidance; planning, capture, question resolution and advisor prompts do not. While working, execution runs the smallest checks that cover the change; the full suite runs at phase boundaries and before completion. It prefers to run independent suites, builds, long commands and agent/LLM test runs in parallel (up to 5), and may make a small runner change for that, with isolated outputs and locked shared counters. Parallelism is a preference, not a goal: shared hardware, files or state, or independence it cannot quickly confirm, stay sequential. Await every result and report failures/unavailable checks; never weaken required checks or count stale results. Rerun affected checks after fixes and ensure required validation covers the final relevant code/input state, without unjustified repeat runs.

The current plan is the session branch's last plan if still open, else the most recently updated open plan. Except for `/plan3 write` and `/plan3 convert`, switching to another plan with more than 20k context tokens compacts first; a failed compaction sends nothing. The footer shows a work-tools marker and an eight-cell progress bar before the counts: `🛠️ Plan [██░░░░░░] 4/15 · S05`. With the subscription footer on, this moves to the end of the first footer row without the marker and hides the extension status row. Percentage reflects completed steps, not elapsed time; plans without steps show 0%.

The agent updates plans with the `plan3` tool: `get`, `title` (renames the file, keeping its 8-hex id), `status` (complete is refused while steps are open and moves the plan to `docs/plans/done/`), `step` (`pending|wip|done|failed|blocked`, optional `note`/`check` lines), `next` (completes the wip step, opens the next), `section` (append or replace), `add` (next free IDs after a step, e.g. JEV-15 → JEV-16, plus an Amendments entry), `ideas` (save/review detailed proposals), and `idea` (reconcile a saved commented response with a rationale). Prose is written with write/edit. Native Edit/Write and Plan3 updates share a per-file, cross-process lock: Plan3 waits for an accepted native write, while an overlapping native edit is rejected with a retry message rather than losing changes. Reread and retry rejected edits after the other operation finishes. This coordinates Pi tools, not external editors or shell writes.

**Plan models** (`/wo → Settings → Plan3 → Plan models`, setting `workOrchestrator.plan3.models`): an ordered list of `{model, thinking}`. The advisor is the first available entry from another model family than the current one (family = first dash token of the model id), so on Opus it picks Astra and on Astra it picks Opus; `all` instead selects every available configured model except the **exact current provider/model**, including same-family models (e.g. Astra from Sol), deduplicated by model. The command announces selected advisors and exclusions; the agent launches them in parallel and must report every result or failure before selection. No eligible entry → the current agent works alone and says so. Running `/plan3 ideas|review` is the only delegation Plan3 authorizes.

Planning prompts require self-contained questions with this Markdown layout (older plain questions still allow direct free-text answers):

```markdown
### Blocking

- **Q-01** Which format should we use?
  - Context: Existing consumers read CSV; changing format requires migration.
  - Recommendation: Keep CSV to avoid migration.
  - Option: Keep CSV — No consumer changes needed.
  - Option: Use JSON — Easier nesting, but all consumers must change.
```

Self-check: `node "scripts/test-work-plan3.mjs"`.

### Architecture diagrams

- Diagrams, the live chat, files and phone access are served by [pi-control-hub](../pi-control-hub), which hosts Pi sessions over RPC; ce-workflow no longer runs a web server. `/plan3 diagram [plan]` (alias `/plan3 uml`) and `/plan3 architecture` point you there. The agent edits diagrams through the revision-checked `plan3_diagram` get/apply tool; affected dependents are reported for follow-up, not changed automatically.
- **Storage:** `<plan>.diagram.json` lives beside its Markdown plan and moves/archives with it. Whole-product data lives at `docs/architecture/product.diagram.json`. These are bounded, validated structured models, not generated SVG screenshots; keep them in Git when useful. Stable ids, revisions and dependency checks preserve agent/browser edits.
- **Completion:** an existing product diagram adds one final `[code]` `ARCH-RECONCILE` step. Completion requires its done mark, including an explicit "no architecture change" outcome; failed/blocked/human is not done. Force finish first asks the live agent to reconcile what was actually built from code/git, rather than unfinished planned slices, then archives. An aborted/failed update leaves the step wip; you may retry or explicitly choose Archive anyway, recording the waiver and possible stale architecture in Amendments. Without a product diagram, Force finish remains immediate.
- **Under the hub:** a hub-started Pi answers the hub's page calls (plan commands, diagram edits, models, usage) through a hidden `/pi-hub` command, and every ask_user question or menu is drawn by the hub. A terminal Pi refuses a session the hub holds.
- **Vendored dialogs:** ce-workflow owns the small pi-ask-user fork, with upstream terminal behavior plus the hub/intercom answer race. Provenance, MIT license and divergences live in `extensions/ask-user/UPSTREAM.md`; package catch-up reviews newer upstream sources without overwriting our fork. A separately loaded ask_user takes precedence and disables our remote-answer integration (warning shown).

## Design sessions

Ask the agent for design variants and it uses the `design` tool. `start` opens one hub session per direction from the same brief (project files go along as read-only `inputs`; `kind` is web, app or deck; `system` names a design system). Each design has a handle (`design-1`, `design-2`, ...) and a folder, `.pi/designs/<handle>/`, which that session's own agent writes (plain HTML by default): `index.html` first, one HTML file per screen, a shared `styles.css` and a `DESIGN.md` with its tokens. Design sessions can write only inside their folder (and `.pi/designs/references/`). They follow a built-in design guide (frontend-design plus craft rules adapted from OpenDesign, Apache-2.0). Set their model under `/wo` → Settings → Design session model (`workOrchestrator.designModel`, `provider/id:effort`); pick a strong one.

Under pi-control-hub every variant is its own hub session, named by its direction (`Calm`, `Bold editorial`) with the brief below (`Home page`) and a 🎨 icon. Its page shows the design live beside the chat, reloaded as files change:

- **Devices**: one picker with Desktop, Phone small/Phone/Phone large, Foldable, Tablet, Laptop and Slide, plus rotate. The frame scales to fit, and the choice is kept per design. This changes size, not the viewer's mouse/touch capability. A screen picker appears when there are several screens.
- **Comment**: click elements to add numbered pins and lines like `(1) index.html @hero-cta <a> "Start free": bigger` to your message, then send once.
- **Edit**: change one element's color, size, spacing or radius live; **Keep** adds a `Set ...` line for the agent to write into the files. A design's own Tweaks panel adds **Keep tweaks** the same way.
- **Mark**: replays the page's declared draft state (device, slide, supported unsaved fields/dialogs and live CSS) in an isolated render, then opens the image annotator. The design must provide `designPreview.capture/restore`; unsupported state, failed replay or mixed touch/fine-pointer hardware reports an error rather than showing a fresh page.
- **Versions**: every turn that changed files becomes a version. ◂ ▸ step through them, and **Restore** asks the agent to bring one back (nothing is lost).
- **Decks**: ‹ N / M › moves through slides, and comment lines name the slide.

The agent checks its work with `look` (headless renders at device presets with a report of overflow, errors and failed files). `reference <url>` captures a site's screenshots and measured colors, fonts and spacing into `.pi/designs/references/<site>/`. `systems` lists the project's own `DESIGN.md` or tokens first, then OpenDesign's brand design systems, and fetches the chosen one into `.pi/designs/systems/<name>/` with the commit it came from.

- **Select** ("select this", or "@design-2" elsewhere): exports the design to `docs/designs/<name>/` with `BRIEF.md` (brief, direction, kind, system, references) and `HANDOFF.md` (screens, tokens, required states, viewports, checklist), stars it (★ on its row) and asks where to implement it: the session it was started from (offered only while it exists) or a new one, which gets a message naming the folder. Selecting again updates the same folder and lists the added, changed and removed files since the last selection (the previous one stays in `.pi/designs/selected/<handle>.before/` for `git diff --no-index`).
- **Clone** (to try another approach): asks a name, then makes a new design with a copy of every file and a hub session forked from this one, chat included. The original is untouched.

Sessions are kept in `.pi/designs/sessions.json`.

### Optional Astryx foundation

- Ordinary HTML and HTML-only decks need no Astryx installation. Explicit `kind: "app", system: "astryx"` starts an experimental React/component design; selecting the Astryx reference for a web design does not convert it into an app.
- The first theme, lookup or component build asks before downloading the reviewed tooling **on the hub host**. The measured Windows install used about 28 MiB of package payloads and 146 MiB of installed files; other hosts can differ. The verified version/platform cache is shared between designs. A cold offline host cannot provision it; a warm intact cache needs neither another prompt nor a download. Integrity verification and builds still take time.
- Remote clients need only their browser, not npm, React, a compiler or developer tools. The browser still needs a connection to the hub: “offline runtime” means no public package/CDN dependency once the cache and all design assets are local. It is not permission to hotlink remote fonts/images and claim offline operation.
- Component agents edit `src/`, screen shells and design notes; the studio owns generated root HTML/assets and the fixed builder. Successful turns, `look`, select, clone and restore share that build boundary. A failed draft is retained, while the last good preview stays visible. Selected handoffs include editable source, exact dependency pins, full notices and rebuild/state instructions, not `node_modules` or host caches. Prototype source is not a production-readiness certificate.
- `theme` emits standalone CSS/JSON without requiring React in the page; its contrast measurements cover named token pairs, not every rendered state. `lookup` searches the installed version and reads requested component/template/theme/doc/hook sections in bounded replies; it never runs upstream scaffold/install commands. Prefer this to guessing APIs or pasting the catalog into every session.
- Local form handlers use native validation and `preventDefault()`; form navigation, popups and downloads remain blocked by the design sandbox. `look input:"touch"` and `reducedMotion:true` test those explicit capabilities; choosing a phone size alone does not. Readiness and named draft states must be declared by the design.

The [full product comparison](docs/proposals/astryx-study/product-results.md) found no efficiency or demonstrated visual win: Astryx took 34 minutes versus final HTML's 11.5 minutes, with 2.13 MB versus 52 kB of runtime assets. It remains an explicit experimental capability, not a faster default. Only the recorded Chromium scenarios are checked; Safari/real-touch and physically remote verification remain open. See the [component and handoff evidence](docs/proposals/astryx-study/app-results.md), [loopback browser/transport measurements and limits](docs/proposals/astryx-study/remote-results.md), [provisioning measurements](docs/proposals/astryx-study/provisioning-results.md) and [upstream/license boundary](docs/upstream/astryx.md).

## Context compaction

In **Settings → Compact**, choose:

- **Ultracompact** (default): existing early compaction, evidence stripping, and code-first/hybrid summaries. Its usual threshold is 150k; smaller model windows reduce it safely. Code-first summaries preserve the direct request.
- **Ultrafull compact**: the same code-first evidence selection and configured **Compaction model** as Ultracompact, but the summary is saved as a real Pi compaction checkpoint, not a transient context cut. It retains Pi's configured recent tail (normally 20k) verbatim, keeping tool calls and results together. There is no rolling payload/thinking stripping before or after the checkpoint. Automatic checkpoints default to 150k after tools finish, safely reduced for smaller model windows. An explicitly configured `workOrchestrator.context.compactAtTokens` overrides this default (`/wo context set 200000` sets it to 200k). Existing Compaction model **None** remains code-only; selecting a model enables the existing hybrid summarizer and fallback. Requires Pi 0.99.1+.
- **Native**: Pi's normal compaction threshold and native summary. No Ultracompact summaries, rolling cuts, or payload/thinking stripping. Legacy Context guard Off now selects this mode too.
- **Native 200k**: Native behavior plus a forced checkpoint by 200k context tokens, lowered to leave proxy/output headroom (about 171k for a 272k advertised window). It uses Pi's own native summary generator and supported `turn_end` checkpoint entries after tool execution, without calling the aborting manual-compaction API during a live turn. Oversized native summarization requests—including manual/native safety compaction—are split using Pi's normal serialization and merged through its native summary prompt. Each request has a two-minute deadline; failure leaves the original transcript intact. Requires Pi 0.99.1+.

**Research suspends automatic Ultrafull checkpoints and the forced 200k trigger**, just as it suspends Ultracompact filtering; native context-limit protection remains. **F8 always forces compaction**, including in research. When busy in Ultrafull, a native mode, or research, F8 queues a checkpoint for the next completed-tool boundary. Settings can be global or project-specific; `/wo context ultracompact|ultrafull|native|native-200k` selects the project mode and `/wo context status` shows it.

Compaction promotes only observed facts (what the code or a tool showed) to project knowledge; decisions and preferences from one task stay in that session's checkpoint, so they cannot steer unrelated work. Short reusable facts can be stored explicitly with `/wo fact add`, found with `/wo fact search`, and browsed newest-first with filtering and deletion via `/wo fact show`. Project facts stay in ignored `.ce-workflow/local/knowledge.jsonl`; user facts use `~/.pi/agent/knowledge/claims.jsonl`. Relevant live claims are injected as bounded untrusted data on ordinary turns, native compaction, and active microcompact filtering. Stale, superseded, rejected, unrelated, or secret-shaped claims are not injected. The model-facing `knowledge` tool can record only observed/inferred claims and cannot alter human/verified claims.

The lightweight modes' summary size is a rolling target, not a license to clip protected chronological user requests or the prior checkpoint. Their local fallback can exceed that target to preserve those records. Oversized hybrid model requests skip the provider and retain local memory instead of entering ACP's preflight summarization loop; exceptionally large verbatim user history may still require native semantic summarization to fit the active context.

Do not install another automatic compaction extension into the same Pi profile. Native modes use Pi's native summary generator; Ultracompact and Ultrafull use the selected code-first or hybrid formatter. Ultrafull is an alternative for comparison, not a verified fix for post-compaction looping.

To see how well compaction keeps context, `node scripts/audit-compaction.mjs [dirs or .jsonl] [--since=YYYY-MM-DD] [--top=N]` scans session logs (default: all of `~/.pi/agent/sessions`) without calling a model. For each compaction followed by more work, it counts files read again whose earlier read was dropped (in the next 40 tool calls, skipping files edited first and SKILL/AGENTS/CLAUDE.md), dropped commands run again, dropped edits made again, questions asked of the user again, and user messages repeating a dropped one or saying "I already said" (timer, Plan3 and wake messages never count as the user). Forked sessions count once. It prints averages per compaction mode and the worst compactions with their session file; the signals are leads to read, not proof.

**When the agent ignores or invents something**, first ask whether the information was in its context. If not, give it the source (a file, docs, a URL). If it was and the agent still contradicts it, the context is likely too full: press F8, or continue in a fresh session from the plan (`/resume3`). Compaction is worth trying here, not a guaranteed cure.

**Compact or hand over?** Same goal, more of the same work (a long debugging session with its failed attempts): compact. A separate job found on the way (an out-of-scope bug or refactor): hand over just that part to another session (intercom `handover` with a stated purpose, or a new `/plan3` request) and keep the current plan going.

Output of hub script timers is kept in summaries as ordinary tool output, not among the 20 user requests kept word for word.
